Tests of the checking programs

These tests check that the verification programs accept valid inputs, reject deliberately invalid ones and recover missing compiled dependencies. RESULTS.json records the twenty-two-result mathematical verification; TOOLING-RESULTS.json records the tests and checking-program identities. The lightweight tests, seven Lean inspection cases and eight Linux fixtures passed. Earlier native macOS and dependency-recovery fixture receipts are retained separately, with their original execution identities.

The two statement-mismatch cases require the exact diagnostic after two successful builds, with the expected exit and no other error. All eight Linux fixtures passed with the current checking programs in the fresh VM.

Lightweight tests

The 25 tests in tools/test_checker.py cover inventories, changed or missing sources, duplicate targets, origins, import separation, configuration identities, axiom restrictions, archive safety, artifact completeness, selection of all twenty-two comparisons and distinct success labels for full and partial runs.

The 13 tests in tools/test_comparator_acceptance.py cover the four required acceptance reports, failed exits, configuration, environment and sandbox command construction. Timeout cleanup uses a mocked process; these tests do not themselves execute a sandbox or kernel.

These tests require only Python 3.12 or later and the repository.

python3 -I -B tools/test_checker.py
python3 -I -B tools/test_comparator_acceptance.py

Compiled Lean inspection

The statement-and-axiom checking program, written in Lean, compares each registered theorem with a separately written expected statement, called its contract. It checks definitional equality with full unfolding transparency: definitions may be unfolded, but merely logically equivalent statements do not count as matching. The expected statements are listed in TARGETS.json. The surrounding Python checks reject missing or duplicate reports, wrong declaration origins and unapproved axioms, including indirect uses of an omitted proof. The fresh-build command also rejects compiler warnings and changed source files.

The seven Lean inspection fixtures require acceptance of a valid theorem and a definitionally equal presentation, and rejection of a merely logically equivalent presentation, indirect admission, custom axiom, changed conclusion and extra assumption. The valid case also tests wrong-origin rejection through the statement-and-axiom checking program and its report checks.

python3 -I -B tools/test_inspection.py

Linux comparisons

The eight Linux fixtures check the following expected outcomes with the pinned tools:

Fixture Expected outcome
Valid theorem Comparator, Lean, Nanoda and con-ron accept.
Extra assumption Rejection for the statement mismatch.
Changed definition and conclusion Rejection for the statement mismatch.
Indirect admission Rejection for sorryAx.
Missing Nanoda Refusal to start because the executable is missing.
Failing Nanoda The regular executable runs and prints its marker; Lean and con-ron accept, Comparator rejects.
Missing con-ron Refusal to start because the executable is missing.
Failing con-ron The regular executable runs and prints its marker; Lean and Nanoda accept, Comparator rejects.

The deliberately failing executables exit 73. Each run records their hashes, invocation markers and log hashes; the full logs remain in its directory. The runtime preflight tests network namespace isolation, denied writes outside the checking directory and permitted scratch writes. The checking process confirms its memory and swap limits.

These cases are generated by tools/test_comparator_runtime.py. The separate examples in verification/fixtures/comparator/ are not the inputs to this suite.

python3 -I -B tools/test_comparator_runtime.py

Native macOS comparisons

The optional local runner has nine small cases using the pinned Lean toolchain: a valid theorem, an extra assumption, a changed definition, an indirect admission, a custom axiom, and missing or deliberately failing Nanoda and con-ron executables. Both failing executables must run and print their markers; Lean and the other checker must accept while Comparator rejects.

Three additional checks cover the required trust acknowledgement, selection of the local toolchain without inherited checker overrides, and an actual timeout.

python3 -I -B tools/test_comparator_local.py --trust-project-code

These tests deliberately run without a sandbox and do not establish sandbox protection. Their success label is PASS_LOCAL_FIXTURES_ONLY.

The complete local command checks all twenty-two results; success is reported as PASS_ALL_TWENTY_TWO_UNSANDBOXED. See the verification guide for this optional procedure and its additional trust requirement.

Dependency recovery

The three dependency-recovery fixtures exercise a wholly absent compiled module, a missing .olean.server, and a missing .ir with the other artifacts retained. Each requires the intended import failure, recovery of the module from pinned sources, and acceptance of a small theorem through the same statement-and-axiom checker. The original cache must remain unchanged.

python3 -I -B tools/test_recovery.py --packages lean/.lake/packages

Source and packet checks

Source checks compare the 409 supplied Lean files with the source inventory, the twenty-three adapter Lean files and twenty-two comparison configurations with the comparison inventory, and the 516 declaration mappings with their contracts. The selected local build/replay closure contains 404 modules. Packet preparation checks source identities and import boundaries; preparation does not verify proofs.

See the verification guide for the mathematical checking scope and reproduction instructions.
